# Continuing consultative core — construction and activation status

Actual actor: Codex in Corporate Chad's conversation, October 17, 2026. No authenticated officer, practitioner or CATE review is claimed.

This increment implements the intended consultation contract rather than treating task tracking as the product. A case starts with the current business model, decision, goal, stage and resource constraints; a beginner diagnostic is optional. It retains profile revisions, questions, evidence descriptions, model-run provenance, prior guidance and actual work drafts. Source context and previous profiles remain preserved so a revised decision can be explained. It extends existing PBS entities/ownership in the existing Systems product database; no enterprise authority root, customer identity system or duplicate database is introduced.

Applied migrations: pbs_consultative_cases_and_bounded_model_runs; pbs_consultative_case_context_revision; pbs_consultative_prior_context_provenance; pbs_consultative_decision_memory_projection. No model request was made. Database rollback tests passed ownership/recovery, changed resources with preserved prior profile, consent, disabled processing, retry/conflict, busy/reservation/caps, service-only result writes, retained failure/history and two-owner/anonymous isolation. Model results were explicitly synthetic administrative fixtures and were rolled back. Zero synthetic businesses remained.

## Prepared but NOT deployed

Dedicated pbs-consultation Edge Function with server-side provider key handling, validated Supabase user, owner-bound case RPCs, strict input limits and selected context. It does not reuse the anonymous executive-status pilot or pretend that a named executive reviewed customer work. Context excludes raw Auth/business/case IDs and credentials; known credential/contact/account-like patterns are rejected. Free text cannot be guaranteed fully de-identified. Do not submit personal customer data, account numbers or third-party confidential material.

A model request requires separately enabled environment controls, verified provider configuration, enabled database policy and explicit versioned customer disclosure acceptance. Proposed outbound data: selected business model/decision/goal/constraints/resource amounts; current question and up to twenty evidence descriptions; selected work text up to 6,000 characters with criteria; and bounded context from the latest four successful consultation turns (summaries, prior stage/decision/constraints/resources, action/rationale and hypotheses). Total serialized context max 20 KB. Full case history is stored privately; only this bounded projection is proposed for the provider. Output uses structured responses, store=false, maximum 3,500 output tokens, no action tools and a 45-second request timeout. store=false is not a promise of zero provider retention.

The response contract requires knowns/unknowns/contradictions, evidence-linked competing hypotheses and tests, one to three decision-changing questions, an actionable recommendation with alternatives/dependencies/resource fit/stop condition, substantive work drafts with assumptions and acceptance checks, criterion-specific work feedback, explicit revision from prior guidance, appropriate funding-readiness continuity and no-purchase/specialist boundaries. It forbids invented evidence, independent outcome verification, required borrowing, guaranteed approval and new tasks that bypass existing server gates. Application validation supplements structured JSON; schema validity alone cannot establish consultation quality.

Retries of a reserved model request do not initiate a duplicate provider call. Failures, uncertain completion and persistence uncertainty are explicit. No canned/rule-based answer is silently substituted and labeled a model consultation. Paid entitlement is not implied by any response or saved case.

Automatic approval review rejected the live Edge Function deployment because it introduces service-role/OpenAI-key bindings and an external customer-data processing path without explicit approval for that exact production deployment/data flow. No alternate deployment or provider-call workaround was attempted. Physical Edge inventory confirms pbs-consultation is absent. This is an activation hold, not evidence that the prepared model service has run.

A proposed submission-review binding is included privately and clearly labeled NOT_DEPLOYED. It is not part of current acceptance evidence. It would bind critique to the actual stored submission/criteria and keep customer declarations separate from server quality decisions; additional SQL acceptance is needed before applying it. Current work-feedback proposals do not write execution acceptance.

## Customer construction screen

Uses the existing account/business selector to create/recover/revise the case directly through deployed owner-guarded RPCs. A dialogue interface supports discovery, work production, review and reassessment; evidence references and actual work/criteria are explicit. Successful future responses have follow-up-answer controls and editable drafts that can be reused for review. Draft edits remain customer-edited/unreviewed. Sign-out and business changes clear the view. A disabled model policy prevents any request and explicitly leaves the question unsent; case context can still be saved. Case downloads are private exports, not authenticated independent evidence. This frontend remains on the existing construction branch, unreleased.
